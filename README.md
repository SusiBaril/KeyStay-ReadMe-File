# KeyStay

A multi-landlord tenant and property management platform. Landlords manage properties, units, residents, leases, billing, and maintenance from a web admin panel, and tenants use a mobile app to view their lease, pay rent, and report problems.

> Personal full-stack project, built end to end: planning, architecture, database design, API, web, mobile, CI/CD, and deployment.

**Status:** In active development.

---

## The Problem

Landlords and property managers often track leases, rent, and maintenance through spreadsheets and chat apps. Tenants have no single place to see what they owe, pay, or report an issue. KeyStay gives landlords one place to run their properties and gives tenants a simple mobile app.

## Users and Roles

| Role                 | Platform               | What they do                                                                                            |
| -------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------- |
| **Landlord / Admin** | Web (and mobile later) | Manage properties, units, residents, leases, billing, payments, maintenance requests, and announcements |
| **Tenant**           | Mobile                 | View lease and balance, pay rent, submit maintenance requests, read announcements                       |

## Key Feature: Tenant Join Code

Landlords do not create tenant accounts by hand. Instead:

1. The landlord picks a unit and generates a one-time invite code.
2. The tenant signs up in the mobile app and enters the code.
3. The tenant is added to that landlord's tenant list, linked to the right unit.

Design decisions behind it:

- Codes are tied to one organization and one unit, so a tenant can never land in the wrong landlord's list.
- Only a **hash** of the code is stored. The landlord sees the plain code once, when it is created.
- Codes are single-use, expire, and can be revoked.
- Redemption is rate-limited to prevent guessing.

## Core Features (MVP)

- Properties and units
- Residents and leases (start and end dates, rent, deposit, status)
- Recurring invoices (rent, utilities, penalties) generated by a scheduled job
- Payment recording, with online payment gateway integration planned after
- Maintenance requests with photos and status tracking
- Announcements and push notifications
- Reports: overdue balances, collections, occupancy

## Architecture

A **modular monolith**: one Express API with clear modules (auth, properties, leases, billing, payments, maintenance, notifications), split into services only if scale demands it.

```
Web Admin (React)  ─┐
                    ├──>  Express API (TypeScript) ──> PostgreSQL
Mobile (Expo)      ─┘            │
                                 ├──> Redis + BullMQ (background jobs)
                                 ├──> Object storage (photos)
                                 ├──> Payment gateway (webhooks)
                                 └──> Push / email / SMS providers
```

## Data Model

```
Organization → Property → Unit → Lease → Invoice → Payment
```

Supporting entities: User, Membership, InviteCode, ResidentProfile, MaintenanceRequest, Announcement, Notification, AuditLog.

Key design choices:

- **Multi-landlord from day one.** Every landlord-owned table carries an `organizationId`, and every query is scoped by it. A user can belong to several organizations through a `Membership` table that holds their role.
- **Money is never stored as a float.** Amounts use exact decimal types.
- **Ledger-style billing.** Charges and payments are immutable entries, and the balance is derived from them.
- **Idempotent payment webhooks,** so the same event delivered twice cannot double-credit a payment.

## Security by Design

- Short-lived access tokens with refresh tokens
- Role-based access control plus per-record ownership checks
- Row-level scoping by `organizationId` on every query
- Dedicated tests proving one landlord cannot read another's data, and a tenant cannot read another tenant's lease
- Secrets kept in environment variables, never in the repository
- Input validation, rate limiting, HTTPS, and an audit log of sensitive actions
- Payment data handled only through a certified gateway, with no card data stored

## Engineering Practices

- Short-lived feature branches merged through pull requests into a protected `main`
- CI on every push and pull request: formatting, linting, type-checking, and build
- Pre-commit hooks that lint and format staged files
- Strict TypeScript across the whole stack
- Database changes tracked as versioned migrations
- Work delivered in thin vertical slices, from UI through API to database
